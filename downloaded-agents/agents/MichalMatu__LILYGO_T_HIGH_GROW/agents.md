## Tech Stack & Key Paths

- **Firmware**: ESP32, Arduino core via PlatformIO, ESP32-SvelteKit framework, PsychicHttpServer (ESP-IDF httpd under the hood), LittleFS for assets.
- **UI**: SvelteKit 2, Vite 5, TypeScript 5.8, Tailwind 4, Vitest + Playwright.
- **Directories**:
  - `src/` – application firmware sources.
  - `lib/framework/` – ESP32-SvelteKit framework (network/services/web plumbing).
  - `interface/` – web UI (run npm scripts here only).
  - `lib/` – libraries.

## HTTP Endpoint Conventions

- Use `/rest/...` for **framework/system** endpoints (WiFi/AP, NTP, security, restart/factory reset, system status, etc.). Avoid renaming existing framework routes.
- Use `/api/...` for **application/product** endpoints (sensors, charts, logs, app config, and all new domains like Automation/Alarms/Integrations/Notifications).
- Authentication stays unified through the framework `SecurityManager` and `wrapRequest(...)` + `AuthenticationPredicates`.
- The UI may call both namespaces: treat `/rest` as “platform” and `/api` as “app”.

## Frontend Embedding (important)

- Firmware builds run `scripts/build_interface.py` (via PlatformIO `extra_scripts`) when `EMBED_WWW` is enabled.
- The script builds the UI and generates `lib/framework/core/WWWData.h` (auto-generated). Do not edit this file by hand.
- `pio run -e esp32dev_*` may trigger `npm install`/`npm run build` under `interface/`; expect builds to take longer after UI changes.

### When to use `uploadfs` (LittleFS)

- With `EMBED_WWW` enabled (current default in `esp32dev_*` envs), the web UI is embedded into firmware via `WWWData.h`, so you typically do **not** need `uploadfs` for the frontend.
- Use `uploadfs` only when you intentionally switch to filesystem-served web assets (i.e. build without `EMBED_WWW`) or when you need to preload additional files into the LittleFS image.
- Commands:
  - Build filesystem image: `pio run -e esp32dev_dbg -t buildfs`
  - Upload filesystem image: `pio run -e esp32dev_dbg -t uploadfs`

## Project Assumptions (pre-release)

- **No migrations**: This is pre-release code; do not design or implement config/history migration paths. If a breaking change is needed, we can reset/rewrite stored data.
- **Bounded alarm history**: Alarm events/history must be a fixed-size ring buffer to prevent unbounded growth (RAM/flash is limited). Never implement an append-only log without a hard cap.

## DRAM & Fragmentation (ESP32 specifics)

- Prefer **streaming** responses for large payloads (CSV, charts, long lists): `PsychicStreamResponse` / `PsychicFileResponse` instead of building a full JSON/CSV in a `String`.
- Avoid `String` in hot-path ring buffers (e.g. in-memory log tail): repeated `malloc/free` fragments heap and reduces “Max alloc” even if “free heap” looks OK.
- In this repo: keep the in-memory log ring buffer entries as fixed-size fields (no `String`) so changing `ringBufferSize` doesn’t leave fragmented heap behind.
- When shrinking containers, remember: `std::vector::assign()` may **not** reduce `capacity()`; use rebuild+swap if you need memory to be returned to heap.
- ArduinoJson v7 note: `StaticJsonDocument`/`DynamicJsonDocument` are deprecated compatibility aliases; don’t assume they provide a fixed stack arena like v6. If hard bounds matter, use streaming or a bounded allocator.

## RTC Memory Cache (deep sleep)

- **Goal**: in deep sleep modes, minimize wake time and battery use by avoiding repeated LittleFS reads/parsing on every wake.
- **Source of truth**: configuration is persisted in **LittleFS** (must survive power loss / reboot / reflashing). RTC memory is only a cache.
- **What to store in RTC**: a small **binary runtime snapshot** needed for normal operation after wake (e.g. rule thresholds, cooldowns, actuator mapping, routing flags). Keep it bounded with compile-time limits.
- **Validation**: RTC payload must use `magic` + `schemaVersion` + `size` + `crc32` (or similar). If invalid or unsupported, fall back to loading from LittleFS.
- **Update points**:
  - After any config change via HTTP (e.g. `PUT /api/...`): save to LittleFS (atomic) and rebuild + write RTC cache.
  - On cold boot / power loss / non-deep-sleep resets: load from LittleFS, then rebuild + write RTC cache.
- **Do NOT store in RTC**: JSON strings, `String`, pointers, `std::vector`, or heap-owned objects. RTC cache must be POD/packed structs only.



## Coding Style, Checks & Examples

- Keep modules small (<300 LOC) and focused; avoid God objects that mix ISR/UI/networking.
- Prefer the existing logging style in the module you touch: framework code uses `ESP_LOG*`, app-level code may use `Serial.*`.
- Be mindful of configured verbosity (`LOGGER_LOG_LEVEL`, `CORE_DEBUG_LEVEL`) across `esp32dev_rel/dbg/test`.
- Manage memory: prefer `const` + flash-resident data, audit `extern` variables, no dynamic JSON for static content.
- DRAM constraints: perform heavy operations **sequentially** (never “everything at once”). Avoid overlapping sensor reads, filesystem operations, and TLS/HTTPS requests.
- Always release resources after an action: close files, call `HTTPClient.end()` (if used), call `WiFiClientSecure.stop()` / `client.stop()`, and avoid keeping long-lived TLS clients unless explicitly required.
- Apply the same mindset to **sensor reads**: keep the read path short and sequential, then release resources so idle state is low-power and low-heap.

### Releasing resources after a sensor read (guidelines)

- **Power gating (preferred)**: if sensors are powered via a GPIO/MOSFET, switch them OFF after the read and put related GPIOs into a safe state.
- **I2C**: do not keep I2C transactions open. Ensure the driver returns and no task holds the I2C mutex. If you intentionally deinit I2C to save power, use `Wire.end()` and re-init with `Wire.begin(...)` before the next read (only do this if nothing else needs I2C in-between).
- **SPI**: always finish a transaction with `SPI.endTransaction()`. If you deinit SPI to save power, use `SPI.end()` and re-init before the next use.
- **FreeRTOS locks**: always `xSemaphoreGive(...)` / unlock mutexes you acquired (FS mutex, I2C mutex, etc.), even on early returns/errors.
- **Filesystem**: always `file.close()` and avoid holding open files across unrelated work.
- **Networking/TLS** (when a read triggers uploads/notifications): always close sockets (`client.stop()`), and finalize higher-level HTTP helpers (`HTTPClient.end()`).
- **Heap/objects**: keep large temporary buffers bounded and short-lived; avoid building large JSON DOMs when you can stream output; avoid `new` in hot paths and ensure temporary objects go out of scope after the read.
- Blocking rules: rely on `millis()` or tasks; heavy work belongs in dedicated FreeRTOS tasks.
- Before committing:
  - Don’t hand-edit generated `lib/framework/core/WWWData.h`.
  - `grep -R "constexpr.*PROGMEM" -n src lib/framework` (if requested).
  - `npx eslint` / `prettier` inside `interface/` when editing UI.
  - Capture stack usage logs if touching tasks/allocators.

### Code Example – Non-blocking `/status` Endpoint

```cpp
// Registers a lightweight handler without dynamic allocations.
void StatusHttpService::attachHandlers(AsyncWebServer &server) {
    server.on("/status", HTTP_GET, [this](AsyncWebServerRequest *request) {
        StatusSnapshot snapshot = _monitor.snapshot();
        StaticJsonDocument<256> doc;
        doc["uptime_ms"] = snapshot.uptimeMs;
        doc["heap_free"] = snapshot.heapFree;
        doc["wifi"] = snapshot.wifiState;
        AsyncJsonResponse *response = new AsyncJsonResponse(false, 256);
        response->getRoot().set(doc);
        request->send(response);
    });
}
```
