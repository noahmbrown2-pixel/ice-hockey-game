# {PROJECT_PREFIX} 项目分析技能

## 功能概述

这个技能用于分析 {SESSION_NAME} 中 **{PROJECT_PREFIX} 项目**（`{PROJECT_PREFIX}-<id>`）的模型执行结果是否完成了 prompt 要求。
与 label 项目分析技能的区别仅在于：项目命名约定、目录布局、文件名/标识串前缀。其他评价规则完全一致。

它负责：收集上下文、调用 `implementation-reviewer(.github\agents\implementation-reviewer.agent.md)` agent 执行分析、将结果写入评价文件。

它不负责：继续实现功能、修复代码、帮模型补完未完成部分。

## 项目命名约定（{PROJECT_PREFIX} 项目）

- 项目名格式：`{PROJECT_PREFIX}-<id>`，例如 `{PROJECT_PREFIX}-123`、`{PROJECT_PREFIX}-150`。**id 不补 0、无 label- 前缀**。
- 项目目录：**无后缀**（目录名直接为 `{PROJECT_PREFIX}-<id>`）。
- 主仓根：`02.work session/{SESSION_NAME}/gitlab source/self-projects/{PROJECT_PREFIX}-<id>/`
- 类型子仓目录：`02.work session/{SESSION_NAME}/gitlab source/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-<类型>/`
- 子仓路径：`02.work session/{SESSION_NAME}/gitlab source/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-<类型>/{PROJECT_PREFIX}-<id>-<类型>-<index>/`
- **Bug修复类型工作副本**：`02.work session/{SESSION_NAME}/gitlab source/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-Bug修复/{PROJECT_PREFIX}-<id>-Bug修复-<index>/{PROJECT_PREFIX}-<id>-Bug修复-<index>/` —— 编号目录内含 bug 的工作代码，供模型修复使用。
- **Bug修复类型参考目录（-ref）**：`02.work session/{SESSION_NAME}/gitlab source/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-Bug修复/{PROJECT_PREFIX}-<id>-Bug修复-<index>/{PROJECT_PREFIX}-<id>-Bug修复-<index>-ref/` —— 与工作副本同级（均在编号目录内），内容为注入 bug 后的初始代码副本，作为「修复参考基准」，供分析时与模型修复结果做 diff 对比。
- 结果根：`02.work session/{SESSION_NAME}/ai-model-result/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-<类型>/`
- 文件主名与文件内标识串均**不带 `A-` 前缀**，直接 `{PROJECT_PREFIX}-<id>-<类型>-<index>`。

## 两种分析模式

根据 `<类型>` 自动选择模式，**两种模式均须读取「模型第 N 次回答内容」以分析对话过程，且分析重心偏向对话过程质量**：

- **源码模式**（默认）：适用于 `0-1代码生成`、`Bug修复`、`Feature迭代`、`代码重构`、`工程化` 、`代码测试`等会真实产出代码改动的类型。
  - 读取提示词文件中的「用户第 N 次提示词」、「模型第 N 次回答 trae session id」以及**「模型第 N 次回答内容」**
  - 结合子仓实际源码与提示词，判断改动是否吻合需求、实现是否合理、有没有更好的做法
  - **同时重点分析对话过程**：推理链路是否清晰、是否存在遗留 todo 未完成、操作步骤是否合理高效
- **会话模式**：适用于 `代码理解`。
  - 源码可能没有改动，主要从「模型第 N 次回答内容」中提取分析/测试结论
  - 用户会继续在对话上下文中提供「模型第 N 次回答内容」（附件或粘贴）
  - 同样重点分析对话过程质量

   脚本内容（写文件时使用）：

   ```python
   import sys, re

   def parse_prompt_file(file_path, round_n=0):
       with open(file_path, encoding='utf-8') as f:
           lines = f.readlines()

       # 定位所有轮次的各段起始行（0-based）
       prompt_lines = {}   # round -> line index
       session_lines = {}
       answer_lines = {}

       for i, line in enumerate(lines):
           m = re.match(r'^用户第(\d+)次提示词', line)
           if m:
               prompt_lines[int(m.group(1))] = i
           m = re.match(r'^模型第(\d+)次回答 trae session id', line)
           if m:
               session_lines[int(m.group(1))] = i
           m = re.match(r'^模型第(\d+)次回答内容', line)
           if m:
               answer_lines[int(m.group(1))] = i

       all_marks = sorted(set(
           list(prompt_lines.values()) + list(session_lines.values()) + list(answer_lines.values())
       ))

       def get_block_text(start_line):
           """获取 start_line 之后到下一个标记行之前的文本"""
           next_marks = [x for x in all_marks if x > start_line]
           end = next_marks[0] if next_marks else len(lines)
           return ''.join(lines[start_line + 1:end]).strip()

       rounds = sorted(prompt_lines.keys())

       if round_n == 0:
           # 列出所有轮次摘要
           print(f"{'轮次':<4} {'有提示词':<8} {'有回答内容':<10} {'SessionID':<40} 提示词摘要")
           print("-" * 90)
           for n in rounds:
               prompt_text = get_block_text(prompt_lines[n])
               has_prompt = bool(prompt_text)
               sid = ''
               if n in session_lines:
                   sid_inline = re.sub(r'^模型第\d+次回答 trae session id[：:]?\s*', '', lines[session_lines[n]]).strip()
                   sid = sid_inline if sid_inline else get_block_text(session_lines[n])
               has_answer = False
               if n in answer_lines:
                   has_answer = bool(get_block_text(answer_lines[n]))
               summary = prompt_text[:60].replace('\n', ' ') + ('…' if len(prompt_text) > 60 else '')
               print(f"{n:<4} {'是' if has_prompt else '否':<8} {'是' if has_answer else '否':<10} {sid:<40} {summary}")
       else:
           # 输出指定轮次详情
           n = round_n
           prompt_text = get_block_text(prompt_lines[n]) if n in prompt_lines else ''
           sid = ''
           if n in session_lines:
               sid_inline = re.sub(r'^模型第\d+次回答 trae session id[：:]?\s*', '', lines[session_lines[n]]).strip()
               sid = sid_inline if sid_inline else get_block_text(session_lines[n])
           answer_text = get_block_text(answer_lines[n]) if n in answer_lines else ''
           answer_start = (answer_lines[n] + 2) if n in answer_lines else 0  # 1-based
           print(f"=== SESSION_ID ===\n{sid}")
           print(f"=== PROMPT ===\n{prompt_text}")
           print(f"=== ANSWER_START_LINE (1-based) ===\n{answer_start}")
           print(f"=== ANSWER ===\n{answer_text}")

   if __name__ == '__main__':
       path = sys.argv[1]
       rnd = int(sys.argv[2]) if len(sys.argv) > 2 else 0
       parse_prompt_file(path, rnd)
   ```

   不带第二个参数时输出所有轮次摘要表，找出「有提示词=是」的轮次列给用户选择。

     **Bug修复类型（特殊 diff）**：使用 `-ref` 参考目录与模型工作子仓对比，不使用主仓根。
     ```
     diff -rq "<参考路径>" "<工作副本路径>"
     参考路径：`gitlab source/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-Bug修复/{PROJECT_PREFIX}-<id>-Bug修复-<index>/{PROJECT_PREFIX}-<id>-Bug修复-<index>-ref/`

     ```
     - `Files <参考路径>/... and <子仓路径>/... differ` → 模型**修改**了该文件（核心分析对象，判断修复是否正确）
     - `Only in <子仓路径>/...` → 模型**新增**了该文件
     - `Only in <参考路径>/...` → 模型**删除**了该文件（需重点关注，可能误删）
     若参考目录（`-ref`）不存在，降级为遍历子仓主代码目录读取核心文件，并在对话中提示用户参考目录缺失。

     **其他源码类型（默认 diff）**：
     ```
     diff -rq "<主仓路径>" "<子仓路径>"
     主仓路径：`gitlab source/self-projects/{PROJECT_PREFIX}-<id>/`
     子仓路径：`gitlab source/self-projects/{PROJECT_PREFIX}-<id>/{PROJECT_PREFIX}-<id>-<类型>/{PROJECT_PREFIX}-<id>-<类型>-<index>/`
     ```
     - `Only in <子仓路径>/...: <文件名>` → **新增文件**
     - `Files <主仓路径>/... and <子仓路径>/... differ` → **修改文件**
     - 忽略 `Only in <主仓路径>` 的条目（模型删除的文件，不在分析范围）
     若主仓目录不存在，退回遍历子仓主代码目录读取核心文件。

     **两种 diff** 均只读取变更文件的完整内容；变更文件超过 10 个时，优先读取与 prompt 关键词最相关的文件。
   - **会话模式**：按需读取，无需 git diff。
8. **分两路分析**：

   **第一步：自行提取「过程操作时间线」**（不调用工具，直接从「模型第 N 次回答内容」原文中梳理）

   将模型做的每一步操作按顺序列出：
   ```
   [1] 工具名 → 操作对象（文件名/目录/命令） → 结果(success/fail)
   [2] 工具名 → 操作对象 → 结果
   ...
   ```
   每行后标注发现的异常（如有）：
   - 🔄 重复读取：与步骤 X 操作对象相同，中间无任何变化
   - ⚠️ 顺序异常：如在读任何文件前已先写 todo/规划
   - ❌ 操作失败或之后有回退/重写
   - 📋 todo冗余：第 N 次调用 todo_write（全程共 X 次）

   **第二步：路线 A — 代码产物质量**（调用 `implementation-reviewer` agent）

   传入：这是第几次对话、当前模式、prompt 原文、模型回答内容原文、子仓代码。  
   要求：判断代码产物是否正确完整地完成了 prompt 要求，给出满意/不满意及具体理由。

   **第三步：路线 B — 对话过程质量**（自行按以下 10 个维度评价，不调用额外 agent）

   **评价规则**：每一条必须引用「过程操作时间线」中的具体步骤编号或模型回答中的具体文字作为证据。禁止使用"操作合理""流程顺畅"等无证据的总结性断言——必须说清楚"在步骤 X，模型做了 Y，因为 Z 所以有/没有问题"。**若某维度无问题**：写"无问题"并附至少一条具体依据。**若有问题**：描述具体表现，引用具体步骤，说明为什么有问题。

   - **维度 1 — prompt 理解**：遍历 prompt 中的每一个明确需求点，逐一核对模型是否识别并处理了（引用步骤编号）；若遗漏或误解，对比 prompt 原文说明偏差。
   - **维度 2 — 目标明确性**：模型是否在动手前明确列出目标？若用了 `todo_write`，规划是否在读文件之前还是之后生成？目标是否在过程中发生变化（哪个步骤）？
   - **维度 3 — 推理精简性**：找出所有重复读取（同一文件在时间线中出现 X 次，步骤几和步骤几，中间是否有实质变化）；找出所有多余中间步骤（步骤 X 对最终结果无贡献）。若无，引用时间线说明整体线性推进。
   - **维度 4 — 输出质量**：最终总结结构是否清晰；是否有重复段落（引用位置）；是否截断；代码块是否完整。若无，写"输出完整，结构正常"。
   - **维度 5 — 任务规划**：用步骤编号概括实际操作顺序（如"[1-3]读文件→[4-6]改代码→[7]验证"）；指出哪些步骤顺序不合理及更好的顺序；特别检查 `todo_write` 是否发生在读任何文件前；是否有先改 A 再改回的回退行为（引用具体步骤）。
   - **维度 6 — 工具使用**：列出工具调用次数统计；逐条指出：重复调用（步骤 X 和步骤 Y 对同一目标，中间无变化）、`todo_write` 冗余调用（全程共 N 次，合理做法是开始一次结束一次）、遗漏调用（按 prompt 应调用但未调用的工具）。每条注明工具名、步骤编号、原因。
   - **维度 7 — 整体流程**：整体是否线性推进还是有回绕（引用步骤范围）；有无明显卡顿（某步之后大量额外操作才继续，指出步骤）；探索/实现/验证/总结各阶段步骤分配是否合理。
   - **维度 8 — 高危操作**：有无覆盖已有文件、删除操作、批量修改未说明影响范围。若无，写"无高危操作"。
   - **维度 9 — 总结准确性**：列出模型总结声称完成的所有项（逐条），逐条核对在操作时间线或代码变更中是否有对应实现；指出夸大（声称完成但找不到对应步骤）或遗漏（已完成但总结未提）。
   - **维度 10 — 虚假完成**：prompt 要求的每项功能是否都有对应代码变更？有无"声称修复了 X 但代码该逻辑从未被修改"的情况。若无，写"无虚假完成"。

   **综合过程判定**：
   - 无重大过程问题（冗余操作、总结失实、顺序混乱等）→ 过程满意
   - 有重大过程问题 → 过程不满意，列出 2-3 个最核心问题（各一句话+引用步骤编号）

   **整体满意度判定**：
   - 代码产物不满意（路线 A）→ 整体不满意
   - 过程有重大问题（路线 B）→ 整体不满意，即使产物满意
   - 两路均无重大问题 → 整体满意

9. 综合两路分析结论，填写输出格式的各字段，写入评价结果文件：
   - 「**不满意的点**」以路线 A（代码产物）的判断为依据
   - 「**过程不满意的点**」以路线 B 的逐维度分析为依据，只写有步骤编号支撑的具体问题，无证据的笼统描述一律不写入
   - 「**过程满意度**」基于路线 B 的综合结论写成 80-100 字连贯叙述
   - **写入前必须检查 Session ID 字段是否为空**。若为空，写入评价块后必须在文件末尾追加一行警告注释并在对话中明确提示用户："⚠️ 警告：本次评价结果的 Session ID 为空，请检查提示词文件中是否缺少 trae session id，并在确认后手动补填。"

## 文件修改字段判定

- **源码模式**：直接使用第 7 步文件系统对比得出的变更文件列表。
